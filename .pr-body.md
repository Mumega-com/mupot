## What it does
1. `seat_select` also returns an opaque **seat handle** once (32 random bytes, base64url; only sha256 stored) -> `seat_handles` (migration 0199).
2. A later request presents it as header `X-Mupot-Seat` (priority) or `_meta["mupot/seat"]` (call `params._meta`, or a `_meta` argument, stripped before schema validation). Never `Mcp-Session-Id`. `openai/session`, `openai/subject`, Codex `threadId` are presence-only hints in the receipt.
3. `resolveAuth` (the single derivation site, see "Design note") calls `applySeatHandle`: one SQL statement matches live handle + the human's live UNBOUND directory grant token + same member + same harness + active consenter + active/non-retired seat + active agent with active dedicated member + live W1 seat token. On match the context is built AS the seat agent (`resolveSeatCapabilities`: human's live grants clamped to min(grant,'member') + the agent's home grant, per-scope max, re-stamped to the agent member; `latentCapabilities` = same set). Zero capabilities, any error, or no match -> the human's ORIGINAL unbound context (never a zero-cap context wearing the agent's id). A non-matching presented handle is ignored and sets `seat_handle_rejected` in the receipt; never 401/500.
4. Legacy agent-bound grants, workspace/im/dashboard channels, harness-less grants, and the curated needs-you profile door never look at a handle.
5. Revocation reach is by TRIGGER (0199), so every path takes effect atomically: agent -> not active/paused (deactivate_agent), member -> not active (archive_row/suspend; consenter AND the seat agent's dedicated member), seat retired. `paused` is not terminal (resolver refuses while paused; un-pause restores).
6. `boot_context.identity_receipt`: `binding_source: 'seat_handle'`, `harness`, `seat {id,label}`, `hints {openai_session, openai_subject, codex_thread_id}` (booleans), `seat_handle_rejected`.
7. Step-0: `console.info` JSON `metric: harness_identity_probe` (flag-gated), first call per grant per hour per isolate: presence booleans, 12-hex hashes, `_meta` key NAMES, clientInfo name, Mcp-Session-Id presence. Never raw values.

## Design note (deviation from the brief, flagged)
The brief named two derivation sites (`buildAuthContextFromPropsInner` and `resolveAuth`). I bind in ONE place, `resolveAuth` -> `resolveSeatSession` -> `applySeatHandle`. Reason: the OAuth handler has no body access (`_meta` lives in the JSON body) and every OAuth request passes through `resolveAuth` after the builder anyway; two sites could diverge. The builder still produces the human's context unchanged (it re-verifies the grant token each request; revoked grant -> 401). `seatBinding`/`seatInputs` on `AuthContext` are deleted from the incoming blob in `resolveAuth`, so the header cannot forge them.

## Attack list (and how each is closed)
1. Forge `x-mupot-auth-context` with `seatBinding`/`boundAgentId` -> `seatBinding`/`seatInputs` deleted at the top; caps re-derived; test `forged blob`, `forged seatBinding on a legacy bound blob`.
2. Use another human's handle on my grant -> `grant_token_id`+`consenting_member_id` pinned; ignored + rejected flag.
3. Same human, other harness -> `harness_id` pinned; ignored.
4. Re-consent (new token id) inherits old handles -> `grant_token_id` pinned; ignored.
5. Handle brute force -> 256 bits; format guard rejects non-43-char values before any read; hashed lookup; `UNIQUE(tenant, handle_hash)`.
6. Handle theft from logs/DB/echo -> only hash stored; test greps every text column of every table, console.info/error/warn/log and tool responses; `X-Mupot-Seat` handle-shaped values are not echoed into ctx.seat labels / enroll URLs (flag on).
7. Legacy bound grant (Rava) hijacked by a handle -> gate on `!boundAgentId`+harness; direct and end-to-end tests; harnessId stripped for bound sessions (W1).
8. Workspace/im/dashboard token + handle -> channel gate; test.
9. Privilege escalation via seat -> clamp to member; org owner/admin human still yields <= member; no admin ever; latent == clamped (tests).
10. Org/department grant reaching another member's home squad -> hasCapability planeCoversScope; explicit test against another member's `kind='home'` squad + positive control on a normal squad.
11. Zero-cap agent context -> fallback to human; test (human demoted off the home squad).
12. Stale handle after deactivation / suspension / retirement -> trigger revokes; and the resolver independently re-checks agent status, member status, seat retired, seat token liveness (tests drop each trigger in turn and still fall back).
13. Re-pointing a handle row -> immutability trigger on every identity column, no-delete, revoked_at one-way; test.
14. Cap exhaustion / unbounded handles -> 32 live per seat with LRU eviction (no lockout) + trigger backstop.
15. Agent explosion by deactivate/create loop -> lifetime `max_total` trigger (above).
16. Session-id confusion -> `Mcp-Session-Id`, `openai/*`, `threadId` never select; test passes the valid handle in each and asserts no bind.
17. Handle through the curated needs-you profile -> `skipSeat` (a test caught a real hole here: header handles used to bind on that door).
18. Probe as a leak/DoS -> presence + 12-hex hashes only, per-isolate sampled map capped at 2000, never throws, flag-gated.
19. `_meta` argument smuggling past strict schemas -> stripped only when flag on and not profile; flag off the strict schema still rejects it (test).
20. Handle presented to `seat_select` -> a bound session gets `not_unbound_directory_session`.
