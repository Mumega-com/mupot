# Runtime dispatch v1 operations

`runtime.dispatch/v1` is the governed seam between Mupot task dispatch and one
external desktop runtime. It separates four facts that must never be collapsed:

1. Mupot delivered a durable inbox row.
2. The exact runtime consumed it.
3. The runtime completed or failed the work.
4. An independent gate approved or rejected it.

## Envelope

The body is generated by Mupot:

```json
{
  "version": "runtime.dispatch/v1",
  "type": "task_dispatch",
  "task_id": "...",
  "dispatch_receipt_id": "...",
  "squad_id": "...",
  "runtime_address": "public-route-address"
}
```

Trust the authenticated inbox row for message ID/sequence, outer sender, target,
project, creation time, lease expiry, and `delivery_attempts`. Reject any body or
local route that disagrees. `runtime_address` is a public Mupot route, never a
Codex/Claude/Cursor thread identifier.

## Receipt call

Call MCP `task_dispatch_runtime_receipt`, or generated REST Action
`POST /actions/task_dispatch_runtime_receipt`, with the exact task, dispatch,
message, attempt, stage, and a lowercase SHA-256 hash of the host's
machine-verifiable runtime-consumption/completion receipt.

Stages:

- `runtime_consumed`: after the intended runtime has consumed the task; task
  becomes `in_progress`.
- `completed`: only after consumption; include result and artifact evidence when
  required; task becomes `review`.
- `failed`: include a bounded reason; task becomes `blocked`.

A `failed` receipt terminally fences the entire dispatch/message across every
later delivery attempt. No later attempt for that `dispatch_receipt_id` can record
`runtime_consumed`, even after restart or re-lease. Recovery requires a separately
governed dispatch, not resurrection of failed evidence.

`completed` also requires a valid explicit `gate:<owner>` backed by a currently
active, credentialed gate agent distinct from the assignee. The member identity
bound to that gate credential must currently hold effective `member` or higher
authority on the task squad through the canonical org, department, exact-squad,
or channel-derived inheritance rules. `/send` requires the operator to provide
the gate and the server verifies the grant plus task-squad authority for
Dispatch-now. Nonexistent, revoked, inactive, cross-squad-without-authority,
assignee-only, observer-only, and `gate:agent-self-completion` gates cannot enter
review. The same checks run atomically with completion so a capability revocation
between precheck and mutation rolls the transition back. Ungated runtime work
stays `in_progress` instead of becoming a zombie review; self-approval is never
inferred.

The operation requires an active agent-bound workspace token for the persisted
assignee. It rechecks the current token, member capability, assignment, project,
message, sender, route, lease, and attempt before every new row and replay.
Mutation audit rows record the framework-derived invocation surface (`mcp` or
`rest`); request headers cannot choose that value.

## Idempotency and recovery

The key is `(tenant, dispatch_receipt_id, stage, attempt)`. Retry the same body
after an uncertain response; Mupot returns the existing receipt after rechecking
authority. Never change a body under an existing key—Mupot returns
`runtime_receipt_conflict`.

If the host restarts after leasing but before consumption, keep the row unread and
let the lease expire or resume from the host's durable dedupe record. If it
restarts after consumption, replay the same `runtime_consumed` call before doing
anything else. Completion replay behaves the same. A changed delivery attempt is
a new key and cannot consume the prior attempt's receipt.

Do not call `inbox_ack` until governed handling is complete. Do not send an ACK to
`mupot-dispatch`; it is a system attribution literal, not an agent identity.

Runtime write responses and ordinary task readers receive allowlisted DTOs only:
stage, attempt, public route,
evidence hashes/artifacts, result/reason, and timestamps. Credential, mutation
audit, message, dispatch-correlation, and private receipt row IDs remain confined
to privileged audit storage. Timeline principal UUIDs are replaced with safe agent
name/slug and gate-decider display labels.

## Disable and rollback

Disable the host receiver first. Existing transport and runtime receipts are
append-only and remain auditable. Rolling application code back leaves migration
0138 additive and inert; old runtimes continue seeing an inbox message, but only
v1-aware receivers may record native runtime stages. No automatic redispatch or
model retry occurs.

## Boundary with Flight-3 delivery

Ordinary task dispatch is not a Flight-3 fenced delivery. Flight-3 additionally
requires objective/flight assignment, runtime-seat generations, encrypted ingress,
registered signing authorities, and signed evidence. Do not manufacture those
facts or weaken that schema to make a plain task fit.

## Local proof

Run:

```sh
npx vitest run tests/runtime-dispatch-canary.test.ts \
  tests/task-dispatch-runtime-receipts.test.ts \
  tests/fleet-bridge.test.ts tests/bus-consumer.test.ts
```

The canary uses local SQLite only. It restarts between intake/consumption and
consumption/completion and proves one transport row, one consumption receipt, one
completion receipt, review, and one independent verdict. It addresses no live
runtime or voice task.
