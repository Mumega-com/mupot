# Mupot v0.30.0 - Stabilized Control Plane

## Goal

Ship Mupot `v0.30.0` as a defensible stable release from one immutable main
commit. The release stabilizes the existing control plane: authorization,
credential rotation, message persistence and visibility, inbox reliability,
release identity, and operational evidence. It does not introduce a new product
surface.

The source already reports `0.30.0`; that is preview version truth, not release
proof. Until every prepublication gate passes, no `v0.30.0` tag or stable GitHub
Release exists and no deployment may be described as stable.

The machine-readable receipt contract is
[`v0.30.0-contract.json`](v0.30.0-contract.json). It owns release-specific
receipt types, phases, SHA bindings, and optional tracker issues. For normalized
version `v0.30.0`, this checked-in file is canonical: inline or alternate-path
contracts must normalize to the same receipt set, phases, types, and five
mandatory SHA paths. Historical versions retain their declared custom-contract
behavior. The checker owns invariant CI, exact-commit, host-bundle, and GitHub
App checks.

## Non-negotiable gates

- The named release PR must be merged to `main`; its merge commit must equal the
  supplied release SHA.
- All required PR checks and all push checks on that exact release SHA must pass.
- `package.json`, `package-lock.json`, `src/version.ts`, this document,
  [CHANGELOG.md](../../CHANGELOG.md), and [ROADMAP.md](../../ROADMAP.md) must
  name `0.30.0` consistently.
- The fresh-install, host, permission, lifecycle, external-PR, recovery,
  release-candidate, and stable-deployment receipts in the contract must pass.
- Release-bound fresh-install, lifecycle, external-PR, and recovery bundles must
  record the exact redacted `/health` identity
  `{ok:true,service:"mupot",commit:<release-sha>,clean:true}` in their designated
  hash-recorded validation step. Caller-authored target labels do not substitute
  for this source observation, and omitting `--release-sha` does not waive it
  when the aggregate evidence already carries a verified target SHA. Only fully
  unbound historical manual bundles may omit source health.
- RC evidence must keep candidate identity and source identity explicit:
  `--version v0.30.0-rc.1` controls tag/prerelease identity, while
  `--source-version v0.30.0` controls package/API/live-health version checks.
  Both identities and the exact live commit fail closed on mismatch.
- The complete exported host directory must pass the read-only manifest verifier
  after being copied into the aggregate evidence directory. Its Host-Go gate must
  be `mupot-host-go-cutover/v1`, record the Mupot/Herdr handoff, and include
  `no_live_sos_wiring`; legacy receipt types are historical evidence only and
  cannot satisfy v0.30 readiness.
- A release-bound Host-Go outer bundle, its nested prior manifest, and every
  nested probe must bind the same release SHA. An unbound historical outer
  bundle cannot admit a bound prior bundle. Host-Go probe, build, export, and
  manifest-check commands must all carry `--release-sha`; export and check fail
  closed if the selected manifest is unbound or names another SHA.
- The live GitHub App and installation exports must contain the exact
  least-privilege permission set and must match the permission receipt hashes.
- Prepublication readiness must report
  `receipt_type:"mupot-v030-prepublication-readiness/v1"` and `status:"pass"`
  before any stable tag or GitHub Release is created.
- Final readiness must report
  `receipt_type:"mupot-v030-release-readiness/v1"` and `status:"pass"` after
  publication and release-integrity verification.

## Evidence commands

Use an isolated checkout at the exact candidate SHA. Replace placeholders with
the separately approved release PR and immutable merge commit.

```bash
npm audit --audit-level=high
npm run typecheck
npm test
node --test fleet-runtime/*.test.mjs
bash scripts/ci-local-evidence.sh
npm run receipt:fresh-install:plan -- --pot <pot> --base-url <pot-url> --operator <operator> --release-sha <release-sha>
npm run receipt:bundle:plan -- --agent <agent> --base-url <pot-url> --out-dir <host-go-working-dir> --export-dir <host-go-export-dir> --release-sha <release-sha>
npm run receipt:bundle:export -- --out-dir <host-go-working-dir> --export-dir <host-go-export-dir> --release-sha <release-sha>
npm run receipt:bundle:check -- --out-dir <host-go-export-dir> --release-sha <release-sha>
npm run receipt:github-app-permissions:plan -- --app <app-slug>
npm run receipt:work-lifecycle:plan -- --pot <pot> --base-url <pot-url> --agent <agent> --task-id <task-id> --release-sha <release-sha>
npm run receipt:external-pr-cycle:plan -- --repo <owner/repo> --agent <agent> --task-id <task-id> --issue-url <issue-url> --pr-url <pr-url> --release-sha <release-sha>
npm run receipt:staging-recovery:plan -- --pot <staging-pot> --base-url <staging-url> --release-sha <release-sha>
npm run receipt:release-candidate:plan -- --version v0.30.0-rc.1 --source-version v0.30.0 --repo <owner/repo>
npm run receipt:stable-deployment:plan -- --version v0.30.0 --repo <owner/repo> --release-sha <release-sha>
npm run receipt:release-readiness:plan -- --phase prepublication --version v0.30.0 --contract docs/releases/v0.30.0-contract.json --repo <owner/repo> --checks-pr <release-pr> --release-sha <release-sha>
npm run receipt:release-integrity:plan -- --version v0.30.0 --repo <owner/repo>
```

After publication and a passing release-integrity receipt:

```bash
npm run receipt:release-readiness:check -- --phase final --version v0.30.0 --contract docs/releases/v0.30.0-contract.json --repo <owner/repo> --checks-pr <release-pr> --release-sha <release-sha>
```

## Release order

1. Done: #1241 landed at exact approved head and its merge commit passed
   post-main CI and CodeQL.
2. Done: obsolete/conflicting #1211, #1217, #1236, and #1238 were closed with
   replacement or deferral evidence; release-excluded branches were preserved.
3. Done: #1250 and #1251 landed the bounded release metadata, receipt tooling,
   and neutral Host-Go evidence contract after exact-head CI, independent review,
   Athena, and direct Hadi merge approval.
4. Done: #1252 landed exact `codex-cli` harness recognition at main
   `55c1c3ef`; it remains preview and does not add a v0.30 stable product claim.
5. Freeze the resulting main SHA and produce fresh-install, migration, browser,
   runtime, MCP, host, permission, lifecycle, external-PR, and recovery evidence.
6. Request separate approval to create and deploy `v0.30.0-rc.1`; collect its
   release-candidate receipt and smoke/soak evidence.
7. Do not merge after collecting the RC receipt. If any correction requires a
   post-RC merge, the prior RC evidence is invalid: land the correction through
   the same exact-head gate, return to step 5, freeze the new main SHA, and
   obtain separate approval for a new RC tag, deployment, and receipt.
8. After confirming that no merge followed the latest RC receipt, request
   separate approval for stable deployment at that frozen SHA and run
   prepublication readiness. If it passes, request separate approval for the
   `v0.30.0` tag and GitHub Release.
9. Run release integrity and final readiness from the published tag checkout.

## Authority boundary

This contract authorizes evidence collection and release preparation only. It
does not authorize merging any PR, creating a tag or GitHub Release, deploying a
candidate or stable build, applying production migrations, or changing
credentials or ACLs.
