## Scope

1. **MCPWP office addon, slices 1–2** (mupot#1580).
   - Slice 1 (T1) — PR #1582, **merged to `main` at `921dbcda`** (two
     adversarial gate rounds; round-2 follow-ups filed as mupot#1587).
     Delivers the `mcpwp-office` `AddonManifestV1` ("WordPress as each pot's
     office"): `kind: 'external_mcp'`, `trustClass: 'external_isolated'`, a
     required `office` department, a `site-operator` agent template/squad,
     one `wordpress_site` connector requirement (accepts `mcpwp`, required,
     write, vault-scoped), and `authorityRequests.surfaceGrants` naming
     three office tools for slice 2 to implement: `office.publish_post`,
     `office.list_pending_approvals`, `office.review_approval`. Health check
     (`src/addons/office/health.ts`) does one SSRF-guarded JSON-RPC
     `initialize` probe against `<site>/wp-json/mcpwp/v1/mcp`. The prior
     `installAddon`-refuses-external_mcp blocker noted below was resolved in
     slice 1's round-2 fix (`migrations/0175_addon_external_isolated.sql`,
     an `isolation_class` `ADD COLUMN` — see that file's header).
   - mupot#1587 (slice 1 round-2 follow-ups) + Slice 2 (T2) — branch
     `flight/office-addon-s2`, PR not yet opened as of this writing. Fixes
     the round-2 P1/P2/P3 findings (health.ts SSRF re-check on the rebuilt
     probe URL; `migrations/0178_addon_isolation_class_immutable.sql` widens
     the two identity triggers to also cover `isolation_class`;
     `archiveAddon` now refuses a non-owner actor when
     `retention.purgeRequiresOwner` is true; a `core_department_collision`
     check refuses an external manifest whose own department collides with
     a native addon's; the approval-policy connector-slot exemption is
     narrowed to `capability:'write'` slots; `isNamespacedUnder` rejects a
     bare `'office.'`/`'office.*'`) and implements the three office tools
     (`src/addons/office/service.ts`, `src/mcp/office.ts`) against the
     manifest slice 1 shipped, gated on an approved `task_verdicts` verdict
     for `office.publish_post`.
   - **New blocker surfaced by slice 2, not fixed there:**
     `src/addons/bindings.ts`'s `preflightAddonBindings` unconditionally
     refuses any `connectorRequirements` entry whose `capability` is
     `'write'` (`capability_mismatch`) — and `addon_connector_bindings
     .capability` is schema-`CHECK`'d to `'read'` only
     (`migrations/0052_addon_bindings.sql`). `mcpwp-office`'s one connector
     slot (`wordpress_site`) is `capability:'write'` — the only write-
     capability connector requirement in the codebase — so this addon
     cannot reach `configured`/`active` through the real
     `configureAddon`/`activateAddon` lifecycle today, independent of the
     `isolation_class` fix above. This is a lifecycle/schema change
     affecting every addon's binding path, not scoped to this one addon —
     Athena's/Kasra-core's call, not a builder's to route around. The three
     office tools are built and tested against the DB state that lifecycle
     would produce once fixed (see `tests/mcpwp-office-tools.test.ts`'s file
     header), but cannot be exercised end-to-end through the admin
     configure/activate buttons until this is resolved.
2. **Auth residuals** (mupot#1583, PR #1583, `flight/auth-residuals`,
   **open, not merged**). `/api/projects` authority becomes the session
   member (`sessionMemberId`), never re-resolved from email; resolver step 4
   (`owner_login_emails`) removed as dead and dangerous; `findUserByEmail`
   fails closed on case-variant collisions; CI ratchet
   `check-member-email-authority-lookup` (allowlist per-file counts); `tests/
   auth-dev-login` rewritten onto the real SQLite harness. See
   [docs/security-model.md](../security-model.md) "Login Identity Attach:
   Exclusive Control" for the surrounding predicate this closes a residual
   gap next to.
3. **Tag `v0.31.0`** once both land, CI is green, and the release gate
   passes. No tag exists yet — do not claim one does.
